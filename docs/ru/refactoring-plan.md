## Цель продукта (зачем это существует)

Владелец архива хранит **очень много видеокурсов** (уроки, записи экрана, слайды + речь). Они занимают неприлично много места; часть файлов может **дублироваться**. Нужно **освободить диск**, чтобы скачивать новые курсы.

Практический смысл инструмента:
1. Находить и (опционально) убирать/помечать **дубликаты**.
2. **Сжимать** оставшиеся ролики так, чтобы слайды/текст читались и речь была разборчива — киношного качества не нужно.
3. Делать это **пачками по папкам** и **быстро** (RTX 4060 Ti / NVENC), без ручного HandBrake на каждый файл.
4. Не тратить время на файлы, которые уже и так хорошо сжаты (порог экономии).

Критерий успеха: гигабайты/терабайты свободного места при приемлемом качестве для обучения, а не «идеальный VMAF».

Техническая подцель: на сэмпле выбрать между **HEVC NVENC** и **AV1 NVENC** (или зафиксировать один профиль), затем полный encode, если есть смысл.

## Принципы

1. **Главная метрика — сэкономленное место**, при «достаточно хорошем» качестве для курсов (читаемые слайды, речь).
2. На тесте сэмпла **не смешивать аудиокодеки** (`-c:a copy`), чтобы не врать про выигрыш видео.
3. **Полный encode — только если выгоднее исходника** (порог экономии).
4. **Пакетная обработка папок** — часть продукта, не «потом когда-нибудь».
5. **Конвейер курса:** default `courses/inbox` → `courses/tmp` → `courses/outbox` внутри проекта; пути **переназначаемы**; имена папок **только English**. См. [ADR-0001](./adr/0001-course-inbox-outbox-tmp.md). Метаданные курса — опциональный [`course.json`](./adr/0002-course-folder-naming.md) в корне (не раздувать путь).
6. **CLI и GUI делят одно ядро** (без копипасты команд FFmpeg).
7. Стек: **Python + uv**, FFmpeg с NVENC обязателен.
8. Не дублировать весь курс на диске без необходимости (мало места — `tmp` только под encode).

### Вопрос 1. Как честно выбирать победителя: с VMAF или только по размеру?

**Суть проблемы.**  
В исходном чате победитель = «у кого файл меньше». Но если у HEVC CQ=28, а у AV1 CQ=32, меньший файл может просто хуже выглядеть. Нам нужно решить, насколько строго измеряем качество в первой версии.

**Что такое VMAF (простыми словами).**  
Это оценка «насколько перекодированное видео похоже на оригинал» (обычно 0–100, чем выше — тем лучше). Считает FFmpeg с фильтром `libvmaf`. Не идеал, но гораздо честнее, чем сравнивать только мегабайты.

| Вариант | Что делаем | Плюсы | Минусы |
|---------|------------|-------|--------|
| **A. VMAF обязателен** | На сэмпле считаем VMAF для HEVC и AV1; победитель с учётом качества и размера | Честный выбор кодека | Нужен FFmpeg с `libvmaf`; тест дольше; сложнее код |
| **B. Сначала без VMAF** | Сравниваем размер при фиксированных CQ + в отчёте пишем: «это не сравнение при равном качестве» | Быстрее сделать MVP | Можно выбрать кодек, который просто сильнее «задавил» картинку |
| **C. Гибрид** | По умолчанию size@CQ; если `libvmaf` есть — включаем VMAF автоматически | Гибко | Два режима поведения, сложнее объяснить пользователю |

**На что влияет:** Фаза 1 (ядро бенчмарка), зависимости, скорость теста, доверие к «победителю».

**Рекомендация под архив курсов:** **B** или **C**.  
Для screencast/слайдов важнее стабильный «достаточно хороший» CQ и прогон тысяч файлов, чем идеальный VMAF на каждом.  
**Принято:** **C** (гибрид) — см. журнал решений #1 (`--vmaf auto|off|on`).

### Вопрос 2. Делать графический интерфейс сразу или сначала только командную строку?

**Суть проблемы.**  
В чате просили GUI. Но GUI без стабильного ядра обычно превращается в копипасту багов (стоп не убивает ffmpeg, интерфейс зависает, прогресс фейковый).

| Вариант | Что делаем | Плюсы | Минусы |
|---------|------------|-------|--------|
| **A. Только CLI в MVP** | Запуск вида `uv run smart-convert video.mp4` | Быстрее до рабочего результата; проще отладка | Нет кнопок «Обзор» / красивого окна |
| **B. CLI + GUI сразу** | Параллельно пишем окно на CustomTkinter | Сразу «как программа» | Дольше; риск чинить UI вместо логики выбора кодека |
| **C. CLI сейчас, GUI следом** | Сначала ядро+CLI, GUI тонкой обёрткой над тем же API | Лучший баланс | GUI появится не в первый день |

**На что влияет:** Фазы 3–4, зависимости (`customtkinter`), сроки.

**Рекомендация под архив курсов:** **C** (CLI сейчас → GUI следом).  
Для сотен/тысяч файлов сначала нужна надёжная пакетная CLI; окно удобно поверх уже работающего ядра.

### Вопрос 3. Только видеокарта (NVENC) или ещё запасной путь через процессор?

**Суть проблемы.**  
У вас RTX 4060 Ti — NVENC быстрый. Но программные кодеки (`libx265`, `libsvtav1`) обычно жмут **эффективнее** (меньше файл при том же визуальном качестве), просто намного медленнее.

| Вариант | Что делаем | Плюсы | Минусы |
|---------|------------|-------|--------|
| **A. Только NVENC** | Сравниваем `hevc_nvenc` vs `av1_nvenc` | Просто; быстро; совпадает с именем проекта | Не самый маленький возможный файл |
| **B. NVENC + CPU fallback** | Если NVENC нет / сломался — пробуем x265/SVT-AV1 | Работает на ПК без подходящего GPU | Больше кода, пресетов, тестов |
| **C. NVENC и CPU как режимы** | Пользователь выбирает: `gpu` / `cpu` / `auto` | Максимум гибкости | Самый большой объём работы |

**На что влияет:** Фазы 1–2, проверка окружения, флаги CLI, время кодирования.

**Рекомендация под архив курсов:** **A (только NVENC)** в MVP.  
Объём архива большой — скорость важнее последних 10–20% сжатия от CPU.  
**Принято:** **C** (`gpu` / `cpu` / `auto`) — см. журнал решений #3.

### Вопрос 4. Что делать со звуком в итоговом файле?

**Суть проблемы.**  
Есть два разных момента:

1. **На тесте сэмпла** звук лучше не трогать (`-c:a copy`), иначе AAC vs Opus искажает сравнение видеокодеков. Это уже зафиксировано в принципах плана.
2. **В финальном полном файле** — отдельный выбор: копировать дорожку как есть или перекодировать для экономии места.

| Вариант | Что делаем в полном encode | Плюсы | Минусы |
|---------|----------------------------|-------|--------|
| **A. `copy` по умолчанию** | Звук не перекодируем | Без потери качества звука; быстрее; честнее смотреть экономию от видео | Если исходный звук огромный (PCM/DTS), файл останется тяжёлым |
| **B. Всегда перекодировать** | Например AAC 128k или Opus 128k | Дополнительная экономия места | Лишняя потеря качества звука; часть «победы» будет от аудио, не от видео |
| **C. `copy`, но с опцией** | По умолчанию copy; флаг вроде `--audio aac:128k` | Гибко | Чуть больше настроек |

**На что влияет:** Фаза 2, размер итогового файла, флаги CLI/GUI.

**Рекомендация под архив курсов:** **C**.  
По умолчанию `copy` (не портим звук и не искажаем экономию от видео). Опция перекодировать речь в AAC/Opus ~96–128k — часто даёт заметную экономию на курсах с «жирным» исходным аудио.
